## 0. 方法

- **ish 指令數 / 週期**：`/usr/bin/time -l`（行程級 PMC，user+內核一起算）。
- **ish 拆帳**：`benchmark/macjit/pmi/`（commit 2d7dffc4）。
  - pmisample 透過私有 kperf 每 200k 條 retired 指令（INST_ALL）觸發一次 PMI，取 PC 和 user stack，ktrace 記錄。
  - ledger.py 把每個樣本記到一行：
    - 落在生成碼上的，依 ISH_JIT_MAP 的角色標籤（g/s/t/r/p/d/R/I/x）分類；
    - 落在 ish 本體上的，依最近一個能辨識的呼叫幀分類；
    - `--dump` 時再用 capstone 把「真實工作」細分為：訪存本身、地址計算、旗標存取、FP 暫存器、PIC 常數。
  - 每張帳本約 4.5 萬到 120 萬個樣本，統計誤差小於 1%。
- **原生指令數**：在 docker 裡對同一批 Alpine aarch64 二進位跑 valgrind callgrind（`pmi/native.sh`），是精確的 user 指令數，也就是 guest 指令數。另外拿到 Dr/Dw/Bc/Bi。
- **原生週期 / IPC**：VM（docker / Apple container）裡沒有 PMU。
  - 估算方式：docker 實測時間 × 3.98 GHz。這個頻率由 macOS 原生 CoreMark 實測得出：3.50G cycles / 0.88 s。
  - 交叉驗證：macOS 原生 CoreMark 45454 it/s，docker 45072 it/s，兩者一致。
  - macOS 原生 python 3.9 和 node 20 的版本與 Alpine（3.12 / 22）不同，只作 IPC 量級參考：python nbody IPC 5.2，node 4.0–4.5。
- **限制**：
  - PMI 有幾條指令的 skid。角色層級的合計可信；「真實工作」的細分以及跨 SBA 模式的逐行比較只看量級。例如 SBA=0 時部分訪存樣本落在 TLB 標籤上，所以 SBA=0 的真實工作看起來偏低。
  - 只取 user 態樣本，宿主內核的指令不在帳內。除了 py_startup（sys 約 7%），其餘的 sys 時間都小於 2%。

### 剩餘 7.7× 的拆解

**每次 python 啟動的成本**
- n = 1 / 2 / 5 / 20 的總指令為 0.68 / 1.12 / 2.46 / 9.15G。
- 每次 python 啟動穩定約 **0.446G**；原生 `python3 -c pass` 是 41.6M，所以單一行程膨脹 10.7×。
- 第一次多出的 0.23G 是 ish 本身加 sh 的啟動。

**翻譯（22%）：主要是每個行程都要重跑的 fiber 前端**
- 原生碼其實已經跨行程共用。ISH_JIT_STATS 在 n=20 時：620k 個 block 中有 588k 命中 PIC registry；原生碼生成時間 n=1 為 22 ms，n=20 也只有 81 ms，之後每個行程約 3 ms。
- 但每個新行程仍要對約 3 萬個 block 重跑 gen（解碼並建立 gadget 列表）、registry 查找、fiber_insert 和 hash 擴容。
- 指令細項：jit_block 5.1%、gen_step 4.0%、malloc/memcpy 4.2%、jit_step_end 1.5%、gen_* 約 3%。

**派發（33%）：每個行程的每條邊第一次都走慢路徑**
- 每個行程的 ctx 槽要重新建立，所以每條邊第一次經過時走 STUB_GENERIC → run loop。
- 指令細項：直接邊 22.6%、run loop 4.1%、冷入口 3.8%。

**時間面（sample(1)，200 次迴圈）**
- 生成碼 28%、派發與 run loop 21%。
- 翻譯 15–18%：gen、jit_block、fiber_block_compile、hash 插入。
- 行程結束與 mm 拆除約 7%：mem_destroy、pt_unmap、asbestos_free、invalidate_range。
- 系統呼叫約 7%：openat、fstatat、mmap、munmap。mmap/munmap 本體 0.9%，execve 0.5%。
- 宿主缺頁 3 次（SBA 窗口預先填充），可忽略。
- 動態連結（ld-musl）的成本在「生成碼」裡面，這次沒有按模組拆開。

### AOT 鏡像（ISH_JIT_RECORD + tools/jit_aot）能吃掉多少

AOT 只取代原生碼生成；已確認 AOT 命中時 `fiber_block_compile` 仍然照跑 gen。

- **session 模式**（一個 ish 實例跑多個行程）：PIC registry 已經共用了，AOT 只能省第一次的約 22 ms，佔 20 次總時間的 ≤ 3%。
- **fresh 模式**（每個指令新開一個 ish）：AOT 可省掉生成時間，約佔單次 70 ms 的 30%。
- 真正大的那塊（每個行程的 gen 加重新連結，約 35–45%），AOT 吃不到。要靠「跨行程的 fiber block 和連結表快取」，也就是按（檔案, 偏移）共用整個翻譯結果與預先連結好的 ctx，而不只是共用原生碼。

- 同樣旗標在 docker 裡：指令從 6.16G 變成 15.17G（2.46×），時間從 0.470 s 變成 1.017 s（2.16×）。

帳本（全部 JIT 層打開）：
- 真實工作從 23.7G 降到 **7.9G**，guest 工作量少了 3 倍；
- 但 **57.8% 的指令卡在 run loop**（cpu_step_to_interrupt、mutex trylock/unlock、native_offload_sym_active、current_pid），還有 7.4% 在宿主函式庫、5.5% 在 fiber_exit。

也就是 V8 產生的碼在 ish 裡幾乎每一塊都退回 run loop，沒有保持鏈結。原因還沒查。推測與匿名 RWX / W^X 翻轉頁面的 block 不能連結或被反覆失效有關。

**這是 node 最大的單一槓桿**：如果 V8 JIT 碼能和一般碼一樣鏈結執行，guest 工作量可再降 2.5×。

**node_compute 在 SBA=1 比 SBA=0 慢 44%（5.80 → 8.34 s）**
- 原因：當時窗口只有 4 GB。V8 用 PROT_NONE / NORESERVE 預留的 pointer-compression cage 和遠端 hint 映射落在窗口外，堆上每一次訪存都是窗口檢查失敗後再走線外 TLB 慢路徑，比 SBA=0 的內聯 TLB 還慢。
- 已在 4c9b3792 修正：
  - 窗口加大到 32 GB（SBA_BITS 35）；
  - V8 的遠端 NORESERVE hint 改放進窗口；
  - mprotect 把 PROT_NONE 預留轉正時納入窗口（adoption）。
- 現在 SBA=1 為 3.42 s，SBA=0 為 5.43 s（−37%）。

**下限與目標（直譯器模式）**
- 合計每 guest 指令 7.17 → 下限約 1.6，可達約 3.6，與 nbody 同一組做法。
- 時間約到 0.25×。

### 4 執行緒比單執行緒還差：已找到根因並修好（3a9fdab6）

- 現象：4 個執行緒是兩兩序列執行的。
  - 最小重現：4 條各自自旋 0.4 s 的執行緒，開始時間是 0 / 0 / 0.40 / 0.40，總時間 0.82 s。
  - ISH_SYSTRACE 顯示主執行緒為第 3 條執行緒堆疊做的 mmap 等了 0.44 s。
- 原因：
  - 執行緒在 run loop 期間一直持有 mem->lock 的讀鎖。
  - 原生碼在 w15 週期計數歸零（1024 的倍數）時才回 run loop；run loop 自己的 `++cycle` 會跨過那個倍數，所以永遠不會回傳 INT_TIMER。
  - 結果是自旋在原生碼裡的執行緒從不放鎖，2f12c267 的 `read_wrlock_behind_writer` 根本沒機會讓步。
  - 改動之前的 build-jit 也一樣，是原本就有的 bug。
- 修法（僅 macOS）：run loop 看到 `mem->lock.writers` 非零就回傳 INT_TIMER。
- 修後：

| 量測 | 修前 | 修後 |
|---|---|---|
| 自旋測試 | 0.82 s | 0.46–0.52 s（4 條全部 0 秒啟動） |
| CoreMark 4t | 約 37k it/s | 約 63–67k it/s（+75%）；4.23 → 2.33 s |
| 1t、nbody | — | 不變 |

- 修後 4t / 1t 時間比 1.12（docker 1.0–1.2）。
- 帳本裡 4t 與 1t 的指令剖面相同，run loop 只佔 0.6%。除了這個 bug，**沒有看到全域鎖、invalidate 或 IPI 競爭**。

## 5. 結論：0.5× 可行嗎

**整體（shell / python / node 各 ≥ 0.5×）在目前架構下不可行。** 誠實的天花板如下：

| 群組 | 現在 | 可達目標全部做完 | 理論下限級（Rosetta 等級的 DBT） |
|---|---|---|---|
| coremark | 0.43–0.46× | **0.6–0.8×**（≥ 0.5 可行） | ~1× |
| shell | ~0.31× | ~0.4–0.45× | ~0.7× |
| python 計算（nbody） | 0.17× | ~0.3–0.35× | ~0.55–0.6× |
| python 啟動 | 0.13× | ~0.25–0.3× | ~0.5× |
| node（直譯器旗標） | 0.14× | ~0.25× | ~0.4×（被旗標的 0.46× 封頂） |
| node（若 V8 JIT 碼能正常鏈結） | — | ~0.3–0.4× | ~0.7× |
| **整體幾何平均** | ~0.2× | **~0.35–0.4×** | ~0.6× |

推算方式：可達目標以「IPC 不變、週期與指令同比例下降」換算。被省掉的多半是便宜指令，所以實際收益可能更低。

**原因**

1. **python / node 需要逼近理論下限才可能到 0.5×，也就是要換一代引擎。** 這兩類負載的時間大頭是：
   - 每次訪存約 5 條的軟體檢查；
   - 每條邊約 8–13 條的 PIC 派發；
   - 每次間接跳轉約 30–40 條的間接派發。
   
   要到 0.5×，需要同時做到：
   - 硬體缺頁 fastmem：16K 宿主頁對 4K guest 頁的問題，要讓權限混合的頁走缺頁模擬；
   - 熱路徑 superblock / trace 的私有翻譯；
   - inline cache；
   - 跨行程的整份翻譯快取；
   - node 還要支援 V8 JIT 碼。
   
   每一項都是幾週到幾個月的工程，而且只有全部疊加才過得了 0.5×。
2. **node 有一半差距與模擬無關**：iSH 為了正確性關掉 V8 的 JIT 層，同機原生下這個設定就已經只有 0.46×。
3. **啟動類負載受「每個行程重做」支配**：gen 前端、重新連結、mm 拆除。AOT 鏡像只能解決其中的原生碼生成，在 session 模式下只省 ≤ 3%。

**建議的優先順序**（依每單位工程量的收益）

1. 無旗標窗口檢查：一併去掉 NZCV 存取；CoreMark 預估 −15% 指令，nbody / node 約 −2–4%。
2. 間接派發 inline cache：nbody 13%、node 9% 的指令。
3. 查清楚 V8 JIT 碼為何掉回 run loop：可能是 node 唯一的大槓桿。
4. 跨行程 fiber 和連結快取：py_startup 和 shell 約 −35–45% 指令。
5. 熱塊私有翻譯加 superblock。

建議把 0.5× 只當作 coremark / 純 C 計算類的目標。python / node 的目標應改成 0.3×。若 Minis Mac 版本要對標 Apple container（1.0×），日常 python / node 場景用 JIT 模擬追不上，應該考慮直接用 container / VM 承載。
